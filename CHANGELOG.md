### 2026-06-02

#### Added

- **Image-availability half of ditbox-for-pipe-events: M-pivot-4 auto-build generalised to all consumers; pipe-events wired with a symmetric trigger.** Closes the second half of the ditbox-for-pipe-events gap (the auth half landed earlier the same day; see the cloud-auth entry below). The existing kaniko auto-build at `src/dit/worker_image.py` — previously scoped to Beam-worker consumers — now serves dit's docker runner identically. **`make dit-cloud PIPELINE=pipe-events` is image-side ready**; live e2e remains user-gated (same shape as M5 / Phase 3 limitations).
  - **`src/dit/worker_image.py` generalisation.** `ensure_worker_image` → `ensure_pipeline_image`; `worker_image_tag` → `pipeline_image_tag` (back-compat aliases kept). The function never produced anything Dataflow-specific — it produced "the pipeline's image" — but the name was coined when only Beam-worker consumption existed. Image namespace, kaniko sub-build, content-addressable lookup, and `dit-<pipeline_commit>` tag scheme all generalise unchanged.
  - **Trigger is symmetric across both consumers.** Build only when `worker_image == default_worker_image` AND the run is `unreviewed`. Otherwise pass through. Reviewed code at the pinned default version is pulled from the canonical upstream registry (`gfw-int-infrastructure/<repo>/<package>:vX.Y.Z`, read-only to dit by IAM); only unreviewed code triggers a fresh build under `gcr.io/world-fishing-827/dit/<pipeline>:dit-<pipeline_commit>`. The earlier-considered asymmetric trigger (a `need_registry_image` switch to force the build for docker-runner cloud runs even with reviewed code) was discarded once we verified that pipe-events publishes canonical versioned images the same way the Beam pipelines do.
  - **`workflows/pipe_events/fishing.py`:** `DEFAULT_IMAGE_TAG` is now the canonical published image at the prod-pinned version (`us-central1-docker.pkg.dev/gfw-int-infrastructure/publication/github-globalfishingwatch-pipe-events:v4.2.17`, matching what `composer-dags-production/dags/core/ais/v3.py` pins). `main()` calls `resolve_run_context` and unconditionally stamps `args.image_tag = ctx.worker_image` — the harness owns image resolution (canonical default for reviewed; auto-built for unreviewed; explicit override unchanged), the workflow just stamps. **`--build-from-source` opts out at two levels**: the docker runner ignores `args.image_tag` and builds the compose `pipeline` service from the mounted working tree (runtime); and `resolve_run_context(build_from_source=True)` bypasses `ensure_pipeline_image` entirely so no kaniko build is incurred for an image that won't be pulled (harness-level — avoids a wasted ~5-min Cloud Build per unreviewed local iteration). No pipe-events repo change.
  - **Pipeline image namespace unchanged**: `gcr.io/world-fishing-827/dit/<pipeline>:dit-<pipeline_commit>`. The prod-infra boundary is preserved: nothing writes to `gfw-int-infrastructure`; the kaniko layer cache at `gcr.io/world-fishing-827/github.com/globalfishingwatch/kaniko-cache` (an existing wf827 path the ditbox + worker-image builds share) is preserved. `docker/worker-image/cloudbuild.yaml`'s `_TARGET: prod` default works for pipe-events without change — its Dockerfile exposes a `prod` stage identical in role to the two Beam pipelines'.
  - **User-gated follow-up:** the live `gcloud builds submit` inside a real ditbox-in-Cloud-Build run, the resulting registry pull, and the docker-in-docker invocation with the auto-built image have not been exercised against live infra in this change. Test surface: 276 total tests; the docker-runner trigger matrix collapsed into the symmetric one (the per-consumer matrices were testing the same thing), `tests/test_pipe_events_fishing.py` gained 4 tests pinning the unconditional `args.image_tag` stamping behaviour.

- **`dit.runners.docker` cloud-auth mode + Cloud Build write-ADC step (the auth half of ditbox-for-pipe-events).** Closes the laptop-vs-cloud auth gap for docker-runner pipelines (pipe-events today; any future docker-runner consumer for free) without touching the pipeline code or the workflow contract. Three execution contexts now converge on the standard ADC path (`/root/.config/gcloud/application_default_credentials.json`) inside the container: **laptop** (workflow mounts the user's `gcp` named volume — unchanged), **production** (GKE Workload Identity via metadata server — reference only, dit doesn't reproduce), **ditbox** (Cloud Build writes a short-lived ADC file to `/workspace`; docker runner bind-mounts it `:ro` at the standard path). The workflow's `volumes=["gcp:/root/.config"]` is unchanged — the cloud-auth mode is **env-triggered** (`DIT_CLOUD_AUTH_ADC` set → on), not a workflow parameter, so the same workflow code runs identically in all three contexts.
  - **Runner changes (`src/dit/runners/docker.py`).** New pure helper `_apply_cloud_auth_mode(volumes)` returns the final `-v` flag list. When the env var is set: any caller-supplied mount whose target is `/root/.config` (or a subdirectory) is dropped (named volume doesn't exist in Cloud Build and would shadow the bind-mount) — drops are logged at INFO — and a `:ro` bind-mount of the ADC file is added at the standard path. Applies to both the `docker run` (published) and `docker compose run` (build-from-source) paths. When the env var is unset, behaviour is byte-identical to today.
  - **`cloudbuild-dit.yaml` write-ADC step.** Generates a **short-lived** ADC at `/workspace/dit-adc.json` from `gcloud auth application-default print-access-token` (run against the Cloud Build SA's metadata-server identity); writes an `authorized_user`-shaped JSON where `token` is the active field and the refresh-related fields are clearly-marked placeholders. **Permanent SA keys are not generated.** If the build outlives the ~60-min token TTL the next BQ call gets a loud `invalid_grant` (the placeholder refresh_token fails the OAuth endpoint) — silent fallback to any other identity is impossible by design. Logging hygiene: no `set -x` during token handling, token passed to python via env (never argv), no `echo` of token contents.
  - **Forbidden alternatives considered:** `service_account` JSON (permanent SA key on disk) — forbidden by spec; `impersonated_service_account` — requires `source_credentials` with a real refresh_token the build SA doesn't have; `external_account` (WIF) — Cloud Build uses direct SA attachment, not WIF.
  - **User-gated follow-up:** the live token-write step has not been exercised against real Cloud Build in this change (same gating as M5 / Phase 3). A future hardening pass would have the build SA impersonate a dedicated narrow-scope SA before issuing the token, rather than re-using the build SA's identity directly.
  - 16 new tests in `tests/test_runners_docker.py` (mocks subprocess; no live docker / Cloud Build). The pipe-events repo + workflow code is **unchanged**.
  - See [`docs/conventions.md`](docs/conventions.md) § "Auth in the cloud path (ditbox)" for the three-context table and the hardening follow-up.

#### Added

- **`dit.runners.docker.run(...)` gains `volumes` + `service`.** `volumes: Sequence[str] = ()` threads `-v <spec>` mounts into both the `docker run` (published) and `docker compose run` (build-from-source) paths — pipe-events authenticates to GCP via a docker named volume `gcp` at `/root/.config`. `service: str = "dev"` makes the build-from-source compose service configurable (pipe-events' is `pipeline`). Defaults keep the two Beam consumers byte-identical (no `-v`, `dev` service).
- **`dit.workflow.add_infra_args` split into `add_dataset_args` + `add_dataflow_args`.** A BQ-SQL pipeline (pipe-events) needs only the dataset knob (`--dest-dataset`); it authenticates via the mounted `gcp` ADC volume, so it uses neither `--service-account` (the Dataflow worker SA) nor the Dataflow placement knobs (`--dataflow-region/temp-bucket/subnetwork`) — all of which live in `add_dataflow_args`. `add_infra_args` is now their composition, so the two Beam workflows' parsed namespace is byte-identical (verified). pipe-events calls only `add_dataset_args`.
- **`dit cache-cancel RUN_ID` + `make dit-cancel RUN_ID=<id>` — clean up a run's Dataflow jobs + output tables (M5a of 6).** `dit.cache.cancel_run(run_id, *, region=None)` (previously a `NotImplementedError` stub) now: (1) **discovers the run's Dataflow jobs by the `dit_run_id` label FIRST** (`gcloud dataflow jobs list --filter=labels.dit_run_id=<id>`) — not the stored `dataflow_job_ids`, which are always `[]` — and cancels every job **not in a terminal state** (`Done`/`Failed`/`Cancelled`/`Drained`/`Updated`); anything else (Running/Pending/**Queued**/Cancelling/…) is cancelled, so a queued job that would otherwise start later is caught. Discovery runs before any row lookup, because an **in-flight run** (the primary cancel target) has a live labelled job but **no cache row yet** (rows are written only on mode completion); (2) looks up **all rows sharing the run_id** (one per mode) via the new `read_rows_for_run` helper, and **if rows exist** (3) **deletes the recorded `output_tables`** at the **table level only** (`Client.delete_table(..., not_found_ok=True)`), skipping with a warning any value that isn't a fully-qualified `project.dataset.table` (so a dataset-shaped or malformed entry can never escalate into a dataset delete — `dit_exp_*` snapshot datasets are categorically out of scope), then (4) `UPDATE`s every row to `status='cancelled'`. Idempotent (tolerates already-gone jobs/tables, terminal jobs). A jobs-list call that *errors* is held distinct from one that returns no jobs: with rows present, cleanup still proceeds (job-cancel skipped, logged loud); with no rows it raises a discovery-failure `RuntimeError` (check auth/region) rather than the unknown-id `ValueError` — so a transient gcloud failure can't masquerade as a typo'd run_id. The `ValueError` fires only when discovery **succeeds** but the `run_id` has **both** no rows **and** no labelled jobs (a genuine typo). `region` defaults to `DIT_DATAFLOW_REGION` → `us-central1`, overridable via `--region` / `REGION=`. New `dit cache-cancel` click command + `make dit-cancel RUN_ID=<id> [REGION=<r>]` target. 16 unit tests in `tests/test_cache_cancel.py` (mocked `gcloud` + BQ; no live infra).
- **Pipe-gaps Dataflow jobs now carry the `dit_run_id` label (+ `dit_commit_sha`, `dit_worker_image_tag`, `dit_launched_by`).** Required for `cancel_run`'s label-based job discovery. Port-visits already stamped these via `--labels=k=v` CLI flags to its in-container process; pipe-gaps submits Dataflow in-process, so the labels are threaded through `_make_config` → `cfg.unknown_parsed_args["labels"]` → the gfw-common `PipelineFactory` → Beam `GoogleCloudOptions.labels` (verified end-to-end).
- **Run cache integration in `workflows/port_visits/ais.py` (M5b of 6).** Port-visits now uses the run cache (previously pipe-gaps-only): mirroring the pipe-gaps pattern, it adds `WORKFLOW_FILE_SHA1`, a mode-aware `canonical_params_dict` (output-affecting fields only: `mode`, `start`/`end`, `source_dataset_stem`, `named_anchorages`, `thinned_message_table`, the **submitter-image identity** (see below), plus `tail_days` for the daily-slice modes — `1_bf` ignores it), `_build_cache_key`, and a `_run_with_cache` adapter over the shared `dit.workflow.run_with_cache`. `resolve_run_context(resolve_digest=True)` now resolves the worker-image digest the cache key needs. An identical `(commit, worker-image digest, workflow-file sha1, params)` tuple reuses a prior run's visits table instead of re-submitting Dataflow; `compare_all` takes the cached-or-fresh FQNs. Behaviour on a cache miss is unchanged. 22 unit tests in `tests/test_port_visits_ais.py`.
  - **Submitter image folded into the cache key (soundness).** A port-visits run loads pipe-anchorages code in two places that both determine output: the **submitter** image (`--image-tag`, builds/submits the Beam graph) and the **worker** image (`--sdk_container_image`). The key already content-addresses the worker image + the local commit; it now also content-addresses the submitter image — for a published image (no `--build-from-source`) by resolving `--image-tag` to a digest (`submitter_image_digest`, falling back to the raw tag with a warning if the registry can't be reached), and for `--build-from-source` by a marker (the image's content is the local commit, already in the key). Without this, two runs with different submitter images but the same worker image + commit would have collided on a wrong cache hit.
  - **Both per-mode output tables recorded for cleanup.** The two-step chain produces a visits table (the comparison target) **and** a per-mode thinned `port_events_*` intermediate; both are now recorded on the cache row (visits first) so `cancel_run` deletes both — previously the intermediate was orphaned. The comparison FQN returned to `compare_all` is unchanged (still the visits table). When `--thinned-message-table` is set (step 1 skipped, external table read), only the visits table is recorded (the external table belongs to the caller). The generic `dit.workflow.run_with_cache` gained an `extra_output_tables` param for this; pipe-gaps passes none → byte-identical single-element `output_tables`.

### 2026-05-28

#### Fixed
- **`make dit-cloud REF=<ref>` now runs the ref's code on the Dataflow workers, not the working tree.** Surfaced by the first live auto-build validation: a `REF=origin/main` baseline silently produced a false `main == fix` equivalence because the workers were running the dirty working tree, not main. Two chained defects:
  - **Worker image was built from the working tree, not the ref.** `dit.worker_image.ensure_worker_image` built the kaniko context from `repo_dir` (the uploaded working tree) regardless of the `--REF` the submitter installed (`git+file://…@<ref>`) — a submitter-vs-worker code mismatch exactly of the kind this machinery exists to prevent. It now materialises the **commit's** tree via `git archive <commit>` into a temp context (new `dit.worker_image._export_commit_tree`), so workers and submitter run the same code. Bonus: untracked files and `.git` are excluded from the build context for free.
  - **`is_unreviewed` couldn't reach `origin/main` inside ditbox.** Its `git fetch origin main` fails in the builder (pipelines' `origin` is an SSH URL with no key there), so it fell back to build-when-unsure → every cloud run treated as unreviewed (wasted worker-image builds for reviewed refs + broken cache reuse). `unreviewed` is now resolved **on the laptop** (`merge-base --is-ancestor` against a freshly-fetched `origin/main`) and threaded into the build as `_UNREVIEWED` → `DIT_UNREVIEWED`, mirroring the existing laptop-side `_PIPELINE_COMMIT` resolution. The workflow reads it (`dit.snapshot._unreviewed_from_env_or_check`) and only falls back to the live check when the env var is absent (local `dit run`). 7 new tests (`tests/test_worker_image.py`, `tests/test_snapshot_module.py`).
  - Unaffected: the dirty-tree common case (no `REF`) was always correct (working tree == snapshot tree == built image). The `--suffix` / cross-version path still computes its own classification (it uses an explicit per-binding `--worker-image`).

#### Added
- **M-pivot-4 of the no-dirty-tree migration landed: auto-built worker images close the submitter-vs-worker gap.** A `--runner=dataflow` run loads pipeline code in two places — the submitter from the (snapshotted) source, but the *workers* from the container named by `--worker-image`. So a run of unreviewed code (snapshot / dirty / unmerged) against the **default** worker image would have the workers silently execute stale published code — a footgun the snapshot mechanism can't fix (the worker image is a separate registry artifact). New `dit.worker_image.ensure_worker_image` closes it: when a run is unreviewed *and* `--worker-image` is the default, it builds a content-addressable worker image from the source via a kaniko Cloud Build (`docker/worker-image/cloudbuild.yaml`, shared cache) tagged `gcr.io/world-fishing-827/dit/<pipeline>:dit-<commit>`, and uses it. "Unreviewed" is now an accurate `git merge-base --is-ancestor origin/main` check (`dit.snapshot.is_unreviewed`) — not just "dirty" — so a **clean feature branch** (committed but unmerged) auto-builds too, and a clean `main` run does *not* (uses the published default). This un-defers the ancestor refinement from M-pivot-3, which is required now that the flag gates auto-build rather than being merely informational. Idempotent (existing tag → skip build); no-op for reviewed code, an explicit `--worker-image`, or the docker runner. Called from both workflows' `main()`, so it covers `make dit-cloud` (a nested Cloud Build inside ditbox) and local `dit run --runner=dataflow` alike. 8 tests in `tests/test_worker_image.py`.

  - The `pipeline_dirty` column + dual-write are intentionally kept (deferred drop).
  - Companion PR in the `pipe-gaps` repo reorders its Dockerfile (deps install before `COPY src`) so cached source-rebuilds are seconds; `anchorages_pipeline` is already correctly layered.
- **`make dit-cloud` is now fire-and-forget by default (`--async`).** It snapshots (if dirty), uploads source, and triggers the Cloud Build, returning a build id in seconds rather than streaming logs until the (now nested-worker-image-build + Dataflow) run completes. - **M-pivot-3 of the no-dirty-tree migration landed: snapshots are now cacheable.** `read_cache` no longer filters `pipeline_dirty = FALSE` — the cache key is content-addressable on `pipeline_commit` (a real or deterministic-snapshot commit SHA), so a repeat run of the same uncommitted code resolves to the same snapshot ref and **hits the cache** instead of recomputing (the ~$10 / 60-min waste the pivot was motivated by). Schema (`migrations/002_unreviewed_code.sql`, idempotent `ADD COLUMN IF NOT EXISTS` + backfill): the legacy `pipeline_dirty` flag is superseded by **`unreviewed_code`** (sharper semantic: TRUE for snapshot refs / unmerged branches, FALSE for merged-to-main; now informational — strict-provenance queries filter it explicitly) plus a new **`pipeline_commit_parent`** column (for snapshot rows, the HEAD the dirty tree was based on, parsed from the snapshot commit message). `dit.cache.CachedRun` renames `pipeline_dirty` → `unreviewed_code` and adds `pipeline_commit_parent`; `write_cache` dual-writes the legacy `pipeline_dirty` column (= `unreviewed_code`) for one release so the NOT NULL constraint and older readers keep working until it's dropped. - **M-pivot-2 of the no-dirty-tree migration landed:** dit runs against a dirty pipeline checkout now **auto-snapshot** instead of erroring. Two paths:
  - `make dit-cloud` against a dirty checkout snapshots it on the laptop (where git-push creds live) via `scripts/snapshot.sh` *before* the Cloud Build submit, then threads the resolved snapshot commit into the build as `_PIPELINE_COMMIT` → `DIT_PIPELINE_COMMIT`. The workflow records that as `pipeline_commit`, so the run is traceable to a pushed `refs/dit-snapshots/<pipeline>/<sha>` ref. `REQUIRE_CLEAN=1` opts out (errors on dirty).
  - Local `dit run --runner=dataflow` against a dirty tree auto-snapshots + pushes in-process (new `dit.snapshot.resolve_pipeline_commit`). `--runner=docker` keeps running against the working tree directly (no remote workers → no snapshot needed). `--require-clean` opts out.
  - `--allow-dirty-tree` is now a **deprecated no-op** on both workflows (logs a warning; removed in M-pivot-4). `--suffix` (manual / cross-version) bypasses auto-snapshot and records git state as-is — `cross_version_ais.py` relies on this for its committed worktree refs.
  - New `dit.snapshot` module + `dit.git_info.git_info` (shared `(short_sha, dirty)` helper). 9 unit tests in `tests/test_snapshot_module.py` cover env-override / clean / dirty-docker / dirty-dataflow-snapshot / require-clean / non-editable-install paths.
- **M-pivot-1 of the no-dirty-tree migration landed:** `make snapshot-<pipeline>` now produces **deterministic orphan snapshots** and auto-pushes them to `refs/dit-snapshots/<pipeline>/<commit-short-sha>` on the pipeline's origin. The mechanism uses a temp-index (`GIT_INDEX_FILE=$(mktemp -t ...)` + `git read-tree HEAD` + `git add -u` → tracked-files-only capture) + `git write-tree` + `git -c commit.gpgsign=false commit-tree` with frozen author/committer dates and identities (epoch 0; `dit`/`dit@local`) so identical tree state always produces the same commit SHA — repeat runs of unchanged uncommitted code resolve to the same ref → cache hits. The parent SHA is recorded in the commit message (`dit snapshot of <40-char-sha>`) so the reproduce context survives even after the ref is later deleted. Push is skipped if `git ls-remote` returns the same SHA at the target ref; refuses with a clear error if the remote ref exists at a different SHA (12-char collision or manual overwrite). Snapshot ref naming uses a 12-char SHA prefix.

  **Three-layer credential-leak defence**, since the snapshot push is automatic and the pipeline repo's origin may be a public GitHub repository:
  1. **`git add -u` (tracked-only).** Modifications + deletions to files already in HEAD enter the snapshot; untracked files (including `git add`-ed-but-uncommitted ones) never do. The convenience alternative `git add -A` was explicitly rejected — it would auto-push any rogue `.env`/`sa.json`/dataset/log in the working tree.
  2. **Pre-push banner** prints the `git diff --name-only HEAD` listing so the user sees exactly which paths are about to land on origin before the push happens.
  3. **Pre-push secret scanner (gitleaks v8.30.1, pinned).** Snapshot tree extracted to a temp dir, `gitleaks detect --no-git --redact --exit-code 1` run against it; any finding aborts before either the commit or the push are created. Required by default — refuses to proceed if gitleaks isn't on PATH and no bypass env var is set. Override is `DIT_SKIP_SECRET_SCAN=1` with a loud `WARNING: secret scan BYPASSED` banner. Pre-baked into ditbox via the Dockerfile.

  The broad `make clean-snapshots` is **replaced** by a surgical `make clean-snapshot PIPELINE=<name> REF=<sha-or-full-ref>` aimed at secret-leak remediation only; snapshots live forever by design (bytes-scale storage in a hidden ref namespace). - **`dit.compare.compare_tables` return value now reflects real table differences.** Previously the shim returned `subprocess.run().returncode`, but `table-check summary` always exits `0` regardless of whether differences were found (it's informational, not assertional).
