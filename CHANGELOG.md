## [Unreleased]

### 2026-05-28

#### Fixed
- **`make dit-cloud REF=<ref>` now runs the ref's code on the Dataflow workers, not the working tree.** Surfaced by the first live auto-build validation: a `REF=origin/main` baseline silently produced a false `main == fix` equivalence because the workers were running the dirty working tree, not main. Two chained defects:
  - **Worker image was built from the working tree, not the ref.** `dit.worker_image.ensure_worker_image` built the kaniko context from `repo_dir` (the uploaded working tree) regardless of the `--REF` the submitter installed (`git+file://…@<ref>`) — a submitter-vs-worker code mismatch exactly of the kind this machinery exists to prevent. It now materialises the **commit's** tree via `git archive <commit>` into a temp context (new `dit.worker_image._export_commit_tree`), so workers and submitter run the same code. Bonus: untracked files and `.git` are excluded from the build context for free.
  - **`is_unreviewed` couldn't reach `origin/main` inside ditbox.** Its `git fetch origin main` fails in the builder (pipelines' `origin` is an SSH URL with no key there), so it fell back to build-when-unsure → every cloud run treated as unreviewed (wasted worker-image builds for reviewed refs + broken cache reuse). `unreviewed` is now resolved **on the laptop** (`merge-base --is-ancestor` against a freshly-fetched `origin/main`) and threaded into the build as `_UNREVIEWED` → `DIT_UNREVIEWED`, mirroring the existing laptop-side `_PIPELINE_COMMIT` resolution. The workflow reads it (`dit.snapshot._unreviewed_from_env_or_check`) and only falls back to the live check when the env var is absent (local `dit run`). 7 new tests (`tests/test_worker_image.py`, `tests/test_snapshot_module.py`).
  - Unaffected: the dirty-tree common case (no `REF`) was always correct (working tree == snapshot tree == built image). The `--suffix` / cross-version path still computes its own classification (it uses an explicit per-binding `--worker-image`).

#### Changed
- **New `dit.workflow` harness module — shared scaffolding for integration-test workflows (no behavior change).** The two workflows (`mode_equivalence.py`, `port_visits/ais.py`) had accreted near-identical harness boilerplate; it's now extracted into `src/dit/workflow.py`: the per-user infra-knob defaults + `add_infra_args(parser)` (the five `--dest-dataset`/`--service-account`/`--dataflow-*` flags identical to both), the `--experiment-id` helpers + `add_experiment_id_arg(parser)`, a `RunContext` dataclass + `resolve_run_context(...)` (the shared `main()` preamble: commit/unreviewed resolution incl. the `--suffix` escape hatch → `ensure_worker_image` → run-id/dit-commit/worker-image-digest), and the generic `run_with_cache(...)` cache wrapper (lifted out of `mode_equivalence.py`). Both workflows now call into it; `mode_equivalence.py` shrank ~270 lines, `ais.py` ~120. **Deliberately left per-workflow** (the "duplicate-until-3-consumers" rule still governs them): the phase/mode logic (`execute_bf/bfd/bftruncate/mutate_recover`), `canonical_params_dict`, output-FQN builders, compare keys, `DEFAULT_WORKER_IMAGE`, and `--bq-temp-dataset`. **Port-visits gains no caching** (still pipe-gaps-only; `run_with_cache` adoption there is the future M5), and `resolve_run_context(resolve_digest=False)` keeps the port-visits path free of the worker-image-digest gcloud call it would never use. 33 new tests in `tests/test_workflow.py`. This lowers the cost of the next workflow (VMS / pipe-events) and is the reusable half of M5.

#### Added
- **M-pivot-4 of the no-dirty-tree migration landed: auto-built worker images close the submitter-vs-worker gap.** A `--runner=dataflow` run loads pipeline code in two places — the submitter from the (snapshotted) source, but the *workers* from the container named by `--worker-image`. So a run of unreviewed code (snapshot / dirty / unmerged) against the **default** worker image would have the workers silently execute stale published code — a footgun the snapshot mechanism can't fix (the worker image is a separate registry artifact). New `dit.worker_image.ensure_worker_image` closes it: when a run is unreviewed *and* `--worker-image` is the default, it builds a content-addressable worker image from the source via a kaniko Cloud Build (`docker/worker-image/cloudbuild.yaml`, shared cache) tagged `gcr.io/world-fishing-827/dit/<pipeline>:dit-<commit>`, and uses it. "Unreviewed" is now an accurate `git merge-base --is-ancestor origin/main` check (`dit.snapshot.is_unreviewed`) — not just "dirty" — so a **clean feature branch** (committed but unmerged) auto-builds too, and a clean `main` run does *not* (uses the published default). This un-defers the ancestor refinement from M-pivot-3, which is required now that the flag gates auto-build rather than being merely informational. Idempotent (existing tag → skip build); no-op for reviewed code, an explicit `--worker-image`, or the docker runner. Called from both workflows' `main()`, so it covers `make dit-cloud` (a nested Cloud Build inside ditbox) and local `dit run --runner=dataflow` alike. 8 tests in `tests/test_worker_image.py`.
  - **Removed:** `--allow-dirty-tree` (both workflows), `dit.git_info.warn_if_worker_image_misses_dirty_tree` (the warning is obsolete — the gap is now closed, not flagged) + its `tests/test_git_info.py`, and the `_dirty` substring in output-table suffixes (every run executes a committed ref, so the suffix is always `<experiment_id>_<commit>_<uuid>`).
  - The `pipeline_dirty` column + dual-write are intentionally kept (deferred drop).
  - Companion PR in the `pipe-gaps` repo reorders its Dockerfile (deps install before `COPY src`) so cached source-rebuilds are seconds; `anchorages_pipeline` is already correctly layered.
- **`make dit-cloud` is now fire-and-forget by default (`--async`).** It snapshots (if dirty), uploads source, and triggers the Cloud Build, returning a build id in seconds rather than streaming logs until the (now nested-worker-image-build + Dataflow) run completes. Pass `WAIT=1` to stream + block on the result (CI exit codes, live debugging). This makes the "trigger a run and close your laptop" model real end-to-end — the nested worker-image build above runs cloud-side, so it adds nothing to laptop wait time.
- **M-pivot-3 of the no-dirty-tree migration landed: snapshots are now cacheable.** `read_cache` no longer filters `pipeline_dirty = FALSE` — the cache key is content-addressable on `pipeline_commit` (a real or deterministic-snapshot commit SHA), so a repeat run of the same uncommitted code resolves to the same snapshot ref and **hits the cache** instead of recomputing (the ~$10 / 60-min waste the pivot was motivated by). Schema (`migrations/002_unreviewed_code.sql`, idempotent `ADD COLUMN IF NOT EXISTS` + backfill): the legacy `pipeline_dirty` flag is superseded by **`unreviewed_code`** (sharper semantic: TRUE for snapshot refs / unmerged branches, FALSE for merged-to-main; now informational — strict-provenance queries filter it explicitly) plus a new **`pipeline_commit_parent`** column (for snapshot rows, the HEAD the dirty tree was based on, parsed from the snapshot commit message). `dit.cache.CachedRun` renames `pipeline_dirty` → `unreviewed_code` and adds `pipeline_commit_parent`; `write_cache` dual-writes the legacy `pipeline_dirty` column (= `unreviewed_code`) for one release so the NOT NULL constraint and older readers keep working until it's dropped. New `dit.snapshot.snapshot_parent` helper. **The migration must be applied to `tech_great_expectations.dit_runs` before the next real run** (`bq query --use_legacy_sql=false --project_id=world-fishing-827 < migrations/002_unreviewed_code.sql`). Test count bumped in `tests/test_cache.py` (read-filter-dropped, dual-write, new columns) + `tests/test_snapshot_module.py` (`snapshot_parent`).
- **M-pivot-2 of the no-dirty-tree migration landed:** dit runs against a dirty pipeline checkout now **auto-snapshot** instead of erroring. Two paths:
  - `make dit-cloud` against a dirty checkout snapshots it on the laptop (where git-push creds live) via `scripts/snapshot.sh` *before* the Cloud Build submit, then threads the resolved snapshot commit into the build as `_PIPELINE_COMMIT` → `DIT_PIPELINE_COMMIT`. The workflow records that as `pipeline_commit`, so the run is traceable to a pushed `refs/dit-snapshots/<pipeline>/<sha>` ref. `REQUIRE_CLEAN=1` opts out (errors on dirty).
  - Local `dit run --runner=dataflow` against a dirty tree auto-snapshots + pushes in-process (new `dit.snapshot.resolve_pipeline_commit`). `--runner=docker` keeps running against the working tree directly (no remote workers → no snapshot needed). `--require-clean` opts out.
  - `--allow-dirty-tree` is now a **deprecated no-op** on both workflows (logs a warning; removed in M-pivot-4). `--suffix` (manual / cross-version) bypasses auto-snapshot and records git state as-is — `cross_version_ais.py` relies on this for its committed worktree refs.
  - New `dit.snapshot` module + `dit.git_info.git_info` (shared `(short_sha, dirty)` helper). 9 unit tests in `tests/test_snapshot_module.py` cover env-override / clean / dirty-docker / dirty-dataflow-snapshot / require-clean / non-editable-install paths.
- **M-pivot-1 of the no-dirty-tree migration landed:** `make snapshot-<pipeline>` now produces **deterministic orphan snapshots** and auto-pushes them to `refs/dit-snapshots/<pipeline>/<commit-short-sha>` on the pipeline's origin. The mechanism uses a temp-index (`GIT_INDEX_FILE=$(mktemp -t ...)` + `git read-tree HEAD` + `git add -u` → tracked-files-only capture) + `git write-tree` + `git -c commit.gpgsign=false commit-tree` with frozen author/committer dates and identities (epoch 0; `dit`/`dit@local`) so identical tree state always produces the same commit SHA — repeat runs of unchanged uncommitted code resolve to the same ref → cache hits. The parent SHA is recorded in the commit message (`dit snapshot of <40-char-sha>`) so the reproduce context survives even after the ref is later deleted. Push is skipped if `git ls-remote` returns the same SHA at the target ref; refuses with a clear error if the remote ref exists at a different SHA (12-char collision or manual overwrite). Snapshot ref naming uses a 12-char SHA prefix.

  **Three-layer credential-leak defence**, since the snapshot push is automatic and the pipeline repo's origin may be a public GitHub repository:
  1. **`git add -u` (tracked-only).** Modifications + deletions to files already in HEAD enter the snapshot; untracked files (including `git add`-ed-but-uncommitted ones) never do. The convenience alternative `git add -A` was explicitly rejected — it would auto-push any rogue `.env`/`sa.json`/dataset/log in the working tree.
  2. **Pre-push banner** prints the `git diff --name-only HEAD` listing so the user sees exactly which paths are about to land on origin before the push happens.
  3. **Pre-push secret scanner (gitleaks v8.30.1, pinned).** Snapshot tree extracted to a temp dir, `gitleaks detect --no-git --redact --exit-code 1` run against it; any finding aborts before either the commit or the push are created. Required by default — refuses to proceed if gitleaks isn't on PATH and no bypass env var is set. Override is `DIT_SKIP_SECRET_SCAN=1` with a loud `WARNING: secret scan BYPASSED` banner. Pre-baked into ditbox via the Dockerfile.

  The broad `make clean-snapshots` is **replaced** by a surgical `make clean-snapshot PIPELINE=<name> REF=<sha-or-full-ref>` aimed at secret-leak remediation only; snapshots live forever by design (bytes-scale storage in a hidden ref namespace). A pytest suite in `tests/test_snapshot.py` covers the property surface (orphan-ness, idempotency under unchanged trees, different trees → different refs, only-untracked-changes treated as clean, no index pollution, surgical clean, untracked-file exclusion, gitignored-file exclusion, ref-divergence detection + no-partial-ref-left-behind, scanner-blocks-on-finding, scanner-allows-clean-tree, bypass-banner-is-loud, refuses-without-scanner-or-bypass). `scripts/snapshot.sh` factored out so the snapshot step is testable independently of `pip install`. The previous `scripts/snapshot-install.sh` (git-stash-based) and `scripts/clean-snapshots.sh` (broad sweep) are gone.


- **Run cache integration in `workflows/pipe_gaps/mode_equivalence.py` (M4 of 6).** Each mode's `execute_*` call is now wrapped in a `_run_with_cache` helper that hashes the `(pipeline_commit, worker_image_digest, workflow_file_sha1, params)` tuple and looks up `tech_great_expectations.dit_runs`. On cache hit (and verified-present output tables), the workflow skips Dataflow entirely and uses the cached FQN for downstream comparisons; on miss, it runs the mode as before and writes a `CachedRun` row at completion. `dit_run_id` (12-hex UUID) is generated once per `main()` and stamped on the cache row alongside `pipeline_commit`, `pipeline_dirty`, `dit_commit`, and the resolved `worker_image_digest`. Dirty-tree runs still write the row (registry purpose) — `read_cache` filters them out of lookups. `dit.compare` API unchanged: workflow resolves the FQN (cached or fresh) before calling `compare_tables`. 12 new unit tests in `tests/test_pipe_gaps_mode_equivalence.py` covering canonical-params shape, cache-key construction, hit/miss/stale semantics, dirty-row writes, and extras-affect-key (for mutate_recover's `restricted_ssvids`). `dataflow_job_ids` left as `[]` for now (TODO M5: runner doesn't return job IDs; cancel_run will need to find them via the dit_run_id label as a stopgap).
- **`dit.cache` BQ write path (M3 of 6).** Implements `CachedRun.to_bq_row` + `write_cache`. `write_cache(row, *, client=None)` issues a **parameterised DML INSERT** against `tech_great_expectations.dit_runs` and blocks on `.result()`; the JSON column uses `PARSE_JSON(@params_json)` server-side over a STRING-typed parameter. DML INSERT was chosen over the streaming API (`insert_rows_json`) because streaming-inserted rows sit in a 90-minute buffer that blocks UPDATE/DELETE — which would break M5's `cancel_run` UPDATE — and is at-least-once (retries can duplicate rows without explicit `row_ids=`). DML INSERT lands in permanent storage immediately, exactly-once, at the same cost (INSERT VALUES scans zero bytes). `to_bq_row` stays as a "render-as-dict" helper for debug/log/serialisation; not on the write hot path. **Dirty-tree handling lives at the read side**, not write: dirty rows ARE inserted (so `make dit-cancel` can find them for cleanup), but `read_cache`'s `pipeline_dirty = FALSE` filter keeps them out of cache lookups. 9 new unit tests + a real-BQ smoke (write → `read_cache` round-trip + immediate DELETE) green.
- **`dit.cache` BQ read path (M2 of 6).** Implements `read_cache`, `verify_tables_exist`, `expires_at_for`, and `CachedRun.from_bq_row` — the surface every cache **lookup** needs. `read_cache` runs a parameterised `SELECT` against `tech_great_expectations.dit_runs` filtered to succeeded, non-dirty, non-expired rows; `verify_tables_exist` batches `INFORMATION_SCHEMA.TABLES` queries one-per-dataset; `expires_at_for` uses `Client.get_table().expires` (handles explicit + dataset-default TTL uniformly). 13 new unit tests against a mocked `bigquery.Client` (SQL shape, ordering preservation, dataset grouping, edge cases). Real-BQ smoke against the empty cache table passes (returns `None`; correctly distinguishes existing vs missing tables). Lazy `bigquery` import inside helper functions so `dit.cache`'s pure surface stays importable without `google-cloud-bigquery`. Cancel (M5) still stubbed (write path landed in the M3 entry above).
- **`dit.cache` module — scaffolding for the content-addressable run cache** (BQ table: `world-fishing-827.tech_great_expectations.dit_runs`). Pure functions implemented (`compute_cache_key`, `sha1_of_workflow_file`, `canonicalise_params`, `resolve_worker_image_to_digest`); BQ-touching functions (`read_cache`, `verify_tables_exist`, `expires_at_for`, `write_cache`, `cancel_run`) raise `NotImplementedError` with TODO markers pointing at the per-milestone PRs that follow. 15 unit tests for the pure surface. BQ schema lives in `migrations/001_dit_meta_runs.sql`; implementation plan in `docs/run-cache-impl.md`. Workflow integration lands in subsequent milestones (M4 = pipe-gaps; M5 = port-visits + `make dit-cancel`).

- **`--thinned-message-table=<FQN>` on `workflows/port_visits/ais.py`.** Opt-in flag that **skips step 1 (`thin_port_messages`) entirely** and points step 2 (`port_visits`) at the supplied table. Use when the change under test lives only in step 2 — typically saves the dominant cost on AIS-full where thin dominates the pipeline. When the flag is absent, behaviour is byte-identical to today (pure opt-in).
- **Same flag on `workflows/port_visits/cross_version_ais.py`** — the wrapper owns it for cross-version runs: snapshots the supplied table at `--pin-source-at` into the experiment's snapshot dataset (`dit_exp_<exp>_internal.port_events_external`, matching how source datasets are pinned today), then passes the snapshot FQN to every binding's `ais.py` invocation. `--thinned-message-table` in user-supplied extras is **always dropped** in cross-version runs (regardless of whether the wrapper flag is set) — the wrapper exclusively owns this knob so the user can never inject an unpinned table on a cross-version run. The wrapper's snapshot is created **without `if_not_exists` idempotence**: re-running an experiment with a different `--thinned-message-table` or `--pin-source-at` fails fast (Conflict) rather than silently using the prior snapshot.

#### Fixed
- **`dit.compare.compare_tables` return value now reflects real table differences.** Previously the shim returned `subprocess.run().returncode`, but `table-check summary` always exits `0` regardless of whether differences were found (it's informational, not assertional). Every successful comparison reported `rc=0`, which `cross_version_ais.py` mapped to verdict `IDENTICAL` — silently hiding all real diffs in cross-version runs. New implementation passes `--output-json` to `table-check`, parses the resulting summary, and returns **`0` if tables are identical (post-tolerance), `1` if any difference is detected**. The exact differing-row count is logged at INFO level; the full per-column delta lives in the JSON `table-check` writes. Backward-compatible for `rc == 0` / `rc != 0` callers (mode-equivalence in `ais.py` and `pipe_gaps/mode_equivalence.py`); cross-version verdict lines now reflect reality. Falls back to the subprocess exit code only when no JSON is written (real subprocess failure). Clamping to `0`/`1` (vs returning the raw count) avoids a subtle bug where `sys.exit(diff_rows)` would have been truncated to 0–255 by the OS — a 256-row diff would have exited with status 0 and incorrectly signalled success.
