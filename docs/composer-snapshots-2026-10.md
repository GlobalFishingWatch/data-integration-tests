# Composer render snapshots as DIT's record of production (2026-10)

Spike for [PIPELINE-4700](https://globalfishingwatch.atlassian.net/browse/PIPELINE-4700) ("how DIT stays in sync when a pipeline changes its CLI or DAG parameters"), 2026-10-23. Everything below was read at composer-dags-production `origin/main` **0a644da** (2026-10-22), with `git show` only.

Code:
- `src/dit/composer.py`: the reader. Stdlib only, never imports or executes composer code.
- `workflows/port_visits/composer_drift.py`: the first consumer, a read-only drift check for the port-visits production target.
- `dit composer-dag <snapshot>`: prints a DAG's tasks as JSON, optionally with the run's dates as placeholders.

This is a point-in-time analysis. Production values change; rerun the check rather than trusting the numbers here.

## 1. Why

DIT hand-copies what production runs:
- the argv builders in `workflows/port_visits/ais.py`;
- `ProductionTarget("ais-v5-datalake")` in `cross_version_ais.py`;
- every workflow's default image.

Nothing tells DIT when those copies go stale. The pipe-anchorages v5 CLI drift (PIPELINE-4699) went unnoticed for months. The working agreement allows reading composer as data, never as code (no `gfw.*`, no airflow). Rendering DAGs ourselves would need airflow and composer's own packages, so DIT needs data that composer already produces.

## 2. What a snapshot is

composer keeps one file per DAG under `tests/render_dags/snapshots/`. Each is generated by composer's `scripts/generate_rendered_dag.py` and says "do not edit this file manually". It holds no imports and no Jinja, only one literal assignment, `rendered_dag = {...}`, with:
- `dag_id`, `dag_folder`, `execution_date`, `data_interval_start` / `data_interval_end`, `dagrun_start_date`, `params`, `filter_tasks`, `filter_attributes`;
- `tasks`: task id to the rendered attributes listed in `filter_attributes`. Every task has `trigger_rule`, `upstream_task_ids`, `downstream_task_ids`, `start_date` and `outlets`. Container tasks also have `image`, `cmds` and `arguments` (the full argv, Dataflow flags included). HTTP tasks and sensors have their own attributes.

composer's CI (`tests/render_dags/test_render_dags.py`) renders each DAG for the snapshot's dates and compares the result with the file through `assert_dicts`. Two properties of that comparison matter for DIT (section 4).

DIT reads a snapshot with `git show <commit>:<path>`, so the composer working tree is never touched, and parses it with `ast.parse` plus `ast.literal_eval` on the assignment's value. At 0a644da all **260** snapshots parse this way, in about 1.7 s, with 3775 tasks, 1779 of them container tasks.

## 4. Limits

1. **One run per snapshot.** Dates are concrete, and Jinja conditionals are resolved to the branch that run takes. Example: `core.ais.v5.backfill` picks the gaps worker machine type by `data_interval_start.year` (a higher-memory type from 2025 on), and its snapshot, rendered for 2026, shows only that branch.
2. **Dates are only partly recoverable.** `dit.composer.templatize` maps each date back to the run's interval. It detects the conventions below and reports the rest.

   | Placeholder | Meaning |
   |---|---|
   | `{start_date}` | the interval start's date |
   | `{end_date}` | the last day inside the interval (end minus one day for a midnight end): inclusive ends such as pipe-anchorages v4 `--end_date` |
   | `{end_date_exclusive}` | the interval end's date: exclusive ends such as pipe-events v8 `--end-date` |
   | `{execution_date}` | the logical date, only where it differs from the interval start |

   Each has a `_nodash` form (`YYYYMMDD`), used in job names. An 8-digit date right after a letter (`_v20240117`) is a table version and is never replaced. A date matching one placeholder is replaced; one matching several is left as written and reported as ambiguous; one matching none is reported as a constant. How the intervals limit this:
   - **135** snapshots have a one-day interval. There `{start_date}` and `{end_date}` are the same day, so every run date is ambiguous. This includes the daily `core_ais_v5`.
   - **56** have an empty interval (start equals end): backfills whose dates come from params. There is no `{end_date}`.
   - **3** have intervals shorter than a day and **66** longer than a day. Only the longer ones settle the start-versus-end question.
   - In **125** snapshots `execution_date` equals the interval end, not its start. These dates are the generator's inputs, not necessarily a real run's, so the execution-date convention of a real run cannot be read off them.
3. **argv order is not verified.** `assert_dicts` sorts lists before comparing, so composer's CI would accept a snapshot with its argv in any order. `parse_argv` pairs `--flag value` tokens by position. That is sound only because the files are generated, not edited.
4. **Only the keys a snapshot holds are checked.** A key missing from a task is never compared, so a snapshot says nothing about attributes it leaves out (environment variables, resources).
5. **No flag grammar.** Without the pipeline's own parser, a bare flag followed by a positional (`-v publish`) reads like `-v` taking a value. `parse_argv` accepts a `bare=` hint. Old pipe-events argv has `-v` followed by another flag, so it parses correctly as written.
6. **Odd arguments.** pipe-publications snapshots write 480 arguments as dicts, which CI checks only partially. The reader keeps them apart (`structured_arguments`) and out of the argv.
7. **Production values only.** There is no staging suffix and no DIT view. Flags DIT owns (outputs, service account, buckets, network) carry production's values. Those values must not be copied into this public repository.

## 5. Port visits: DIT against production

Run with `dit run workflows/port_visits/composer_drift.py` (exit 1 means drift was found). DIT is configured as `--baseline-production` configures it: the target's tables, its history start, and the snapshot run's dates.

### 5a. `ProductionTarget("ais-v5-datalake")`

The target finds the job of the daily DAG `core.ais.v5`. Results against `core_ais_v5` (daily) and `core_ais_v5_backfill`:

| Field | Daily | Backfill |
|---|---|---|
| `dataflow_project`, `dataflow_region` | match | match |
| `job_name_prefix` | match | differs: the backfill DAG names its jobs `core-ais-v5-backfill--...` |
| `output_table` | match | match |
| `thinned_table` (step 1 output and step 2 input) | match | match |
| `segment_info_table` | match | match |
| `segs_activity_table` (the one table in `--bad_segs`) | match | match |
| `history_start` (2012-01-01, a constant, not tied to the interval) | match | match |
| `deployed_version` (pipe-anchorages v4.6.4) | match | match |

The brief asked for a comparison with `core_ais_v5_backfill`. The target was written from `dags/core/ais/v5.py`, which defines both DAGs, and its job-name prefix is the daily DAG's. So the backfill's prefix difference is expected, not drift.

The backfill (a 226-day interval) settles the date conventions that the daily snapshot leaves ambiguous:
- step 1 runs `{start_date}` to `{end_date}`;
- step 2 runs from the constant 2012-01-01 to `{end_date}`;
- job names end in `{start_date_nodash}`;
- the `run_date` label is `{start_date}`.

That confirms `ProductionTarget.job_name(D)` (prefix plus D) and the inclusive `--end D` of the production baseline.

`core_ais_v3` differs: its job names end in the interval END (the execution date). Both `{end_date_exclusive}` and `{execution_date}` fit, so the reader reports it as ambiguous. A core AIS v3 target (README roadmap 7c follow-up) needs that settled, from the DAG source or a multi-day snapshot, before `job_name(D)` is written.

### 5b. argv flags, DIT's v4 builders against production

Both steps run the same command (`pipe-anchorages thin_port_messages`, `pipe-anchorages port_visits`).

| | `thin_port_messages` | `port_visits` |
|---|---|---|
| Same | `--start_date`, `--end_date`, `--project`, `--region`, `--sdk_container_image`, `--wait_for_job` | the same, plus `--thinned_message_table`, `--vessel_id_table`, `--bad_segs` (SQL byte-identical) |
| DIT-owned, expected to differ | `--output_table`, `--job_name`, `--labels`, `--service_account_email`, `--temp_location`, `--staging_location`, `--subnetwork`, `--max_num_workers`, `--temp_dataset` (DIT only) | same |
| Only in production | `--disk_size_gb`, `--worker_machine_type`, `--dataflow_service_options` (lineage), `--network`, `--no_use_public_ips` | same |
| Values differ | `--runner`; `--anchorage_table`; `--input_table` | `--runner` |
| Only in DIT, outside the DIT-owned set | none | none |

Notes for the owner, who decides. Nothing was changed.
- **`--runner`.** DIT passes `DataflowRunner`, production passes `dataflow`. Beam's `create_runner` matches partial runner names, per Beam's runner guide, so these should select the same runner. Not verified against the v4.6.4 image.
- **Production-only flags.** These are sizing and networking flags: worker disk and machine type, private IPs and network, a lineage service option. None should change output. Machine type matters for out-of-memory behaviour at production scale, which DIT's 4-worker default never reaches.
- **Step 1 tables.** `ProductionTarget` has no messages or named-anchorages table, because the production baseline runs step 2 only. So DIT's step 1 shows its staging defaults. Production v5 also reads a newer named-anchorages version (2026) from another project. Production v3 reads DIT's default version (v20240117), but from another project too. A step-1 production baseline would need both tables in the target.
- **`DIT_OWNED_FLAGS` is a proposal.** The list (in `composer_drift.py`) is my reading of which differences are deliberate.

## 6. Version drift visible in the snapshots

Image tags are each task's pinned version, and `cmds` + `arguments` give the command names, so both kinds of drift are visible without reading pipeline code (`dit.composer.pinned_versions`).

| Pipeline | DIT drives | Production `core.ais.v3` | Production `core.ais.v5` (+ backfill) |
|---|---|---|---|
| pipe-anchorages | v4.6.4, v4 CLI (`thin_port_messages`, `port_visits`) | v4.6.4, same commands | v4.6.4, same commands. The VMS DAGs also pin v4.6.4. |
| pipe-events | v4.2.17, entrypoint `pipe`: `incremental_events`, `incremental_filter_events`, `auth_and_regions_fishing_events`, `fishing_restrictive` | **v5.0.0**, same entrypoint and command names | **v8.0.1**, entrypoint `pipe-events`, renamed commands (`fishing_events_incremental`, `fishing_events_incremental_filter`, `fishing_events_auth_and_regions`, `fishing_events_restrictive`), hyphenated `--key=value` flags, exclusive `--end-date` |
| pipe-gaps | v0.10.0 worker image, `detect` | **v0.10.3**, `detect` / `publish` | **v0.17.0**, `raw-gaps` / `gap-events` |
| pipe-encounters | v4.4.0 (`create_raw_encounters`, `merge_encounters`) | v4.4.0, same commands | **v4.6.0**, same commands (`create_raw_encounters`, `merge_encounters`) |
| pipe-segment | v5.0.3 | v5.0.3 | no AIS task; VMS v5 pins v5.0.3 |

So yes: the snapshots show that production pins pipe-anchorages v4.6.4, and that DIT's pipe-events and pipe-gaps pins differ from production's in version and, for v5, in command names.

**Correction to the brief.** It gave production v5 as EVENTS v6.2.0 and gaps v0.12.0. Those were `core.ais.v5`'s pins from 2026-08-21 (composer `de9b8564c`) until September: gaps went to v0.12.2 on 2026-09-12 (`cc275168d`) and events moved on 2026-09-21 (`81cba5ccb`). At 0a644da the DAG source pins EVENTS v8.0.1 and GAPS v0.17.0, and the snapshots agree.

DIT's pipe-events pin is stale even against v3: `core.ais.v3` left v4.2.17 on 2026-05-25 (`d6202bca7`). Its gaps pin (v0.10.0) matched v3 from that day until 2026-06-04 (`6666f0d64`, v0.10.2).

## 7. Proposed next steps for PIPELINE-4700

In order of value per effort:

1. **Version-drift check for every workflow (small, do first).** Map each workflow's default image to the snapshot(s) and task(s) it mirrors. Compare its tag and command names with `pinned_versions` and the parsed positionals. This alone would have flagged the pipe-events and pipe-gaps drift above, and production's eventual move to pipe-anchorages v5. It only needs image tags and command names, so it exposes no infrastructure.
2. **Generalise `composer_drift.py` into a `composer-diff` check.** Each workflow declares three things: its snapshot task, the DIT configuration that mirrors it, and its DIT-owned flags. The check diffs DIT-emitted argv against production's. Where it runs is open:
   - composer is private, and whether `automated-testing@` can clone it is unverified;
   - a laptop or scheduled run against a fetched checkout works today;
   - a hook in composer's CI would catch drift at the source.
3. **Owner decisions on section 5b.** Decide on `--runner`, the production-only sizing and networking flags, and the `DIT_OWNED_FLAGS` set. Then the port-visits check passes (exit 0) and stays a regression guard.
4. **Generate `ProductionTarget` from the snapshot.** The fields map one to one (section 5a proves the mapping). The run-date convention needs a multi-day snapshot or the DAG source, because daily snapshots are ambiguous. Keep the hand-written target until the drift check has run green for a while, then generate it, or keep both, with the check as the test.
5. **Checked-in `params/<pipeline>.yaml` at a pinned composer commit.** This is Phase 4 of `docs/plan.md`. Templated argv (placeholders instead of dates) renders back with DIT's own dates (`render_template`). The repo is public, so an allow-list is mandatory: versions, commands, flag names, and the tables DIT targets. Never infrastructure values. Reviewed diffs on regeneration are the sync mechanism. Worth it once two or more workflows consume more than versions and commands; until then, step 1 and step 2 read the snapshot live.
6. **CLI-generation adapters (v4 / v5).** The snapshot shows which generation production runs (image version plus command names: `thin_port_messages` is v4, `port-state-transitions` is v5). It does not show the other generation's argv: a PR on v5 has no snapshot while production is on v4. So the builders stay hand-written per generation. The production generation gets a golden test (snapshot argv rendered with DIT's dates against the builder's output), and a cross-version run picks each binding's adapter by its version. When production moves to v5, the v5 builder gets its golden test from the snapshot instead of from pipe-anchorages main.

**Recommended next step:** item 1 (version-drift check across all five workflows), together with the owner's decisions in item 3.
